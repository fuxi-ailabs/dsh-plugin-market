DT VERIFY

把 Spec，
变成有证据的验收结论。

在 DSH 会话中按 Spec 整理验收要求，生成并统一审查验证计划，用 Harmony 单元测试和界面测试验证鸿蒙工程，最后逐条汇总结论与原始证据。

HOW IT WORKS

从需求到结论，每一步都能回查。

01 / 准备

冻结来源

读取鸿蒙工程、Spec 和可选的 Android 行为基线，生成本次运行的来源快照。之后都从这份快照回查原文，不读取新版本。

“Spec 在 /absolute/spec。”
02 / 输入

统一验收输入

把需求整理成带追溯 ID 的验收项，写清预期、前置条件和来源引用；判断不了的预期标为待复核，不替调用者补答案。

“缺少依据的要求保留未验证。”
03 / 计划

编写测试与统一审查

UT/UI 插件为分到的要求编写测试并提出候选计划；统一审查逐项给出接受或拒绝的理由，没覆盖到的要求保留为缺口。

“只做到正式计划接受为止。”
04 / 执行

执行与汇总

按正式计划执行，每次执行独立留档；汇总时再次复核原始证据。有效失败不会被重试的通过覆盖。

“返回结果文件与证据位置。”

VERIFICATION METHODS

两种验证方式，测试都写在工程里。

UT

Harmony 单元测试

在模块的 src/ohosTest 下编写 Hypium 单元测试。提交计划前核对注册的用例并编译测试 HAP，再在设备或模拟器上执行。

UI

Harmony 界面测试

按页面编写 Python 测试脚本，放在 src/ohosTest/ui-scripts 下，断言写成脚本自己的 assert。门禁检查后每项起一个 Python 进程直接执行，宿主离线复算观察值和点击。

REPAIR

失败后修复

修复是 UT/UI 插件的一个阶段，只在调用者授权时进行：按失败包修改生产代码并全量复测。不改测试；判断测试本身有问题时提出申诉，重新审查。

AGENTS

子 Agent 并行

测试编写可按功能组或页面拆开，修复可按工作项拆开，由随包的 4 个子 Agent 角色执行；宿主不能委派时按顺序处理。

READING THE RESULTS

状态和结论，分开记录。

测试跑没跑成，和需求有没有被满足，是两个问题。汇总文件按验收项同时给出两者，并附上原始证据的位置。

PASS
测试按计划执行并通过。
FAIL
测试执行了，结果与预期不符。
BLOCKED
缺少环境、设备或前置条件，没能得到有效结果。

每条验收项的结论

SATISFIED
有充分证据表明要求被满足。
VIOLATED
有效证据表明要求被违反。
UNVERIFIED
证据不足、执行受阻，或只有反证没有正证；不会被其他项的通过补齐。

IN YOUR WORKFLOW

装好插件，在会话里发起验证。

插件随包提供 dt-verify Skill、验证运行资源和 4 个子 Agent 角色；模型、会话和工具权限沿用 DSH 本身的设置。

适用工程
鸿蒙（HarmonyOS）Stage 工程。被测路径须是工程根目录：含 build-profile.json5，且至少有一个带 src/main/module.json5 的模块。
运行时
DSH 0.2.1-rc.2（包声明兼容 ^0.2.1-rc.2）；Node 22.22 以上的 22.x、24.x 或 26 及以上；pnpm。
Harmony 环境
HarmonyOS SDK、hvigor、ohpm、hdc，以及设备或模拟器。
UI 额外要求
Python 3.11 及以上，用 DT_VERIFY_PYTHON 指定解释器；脚本用到 Hypium 驱动时需要 Hypium 6.1.0.210 与 xdevice。

四个步骤开始使用

  1. 安装插件

    在「插件 → 发现」中找到“DT 验证组件”并安装，安装后重启 DSH。

  2. 配置模型与工作区

    在「设置 → 模型」中配置模型凭据，用标准 preset 新建会话。工作区建议直接选被测鸿蒙工程的根目录（不是 entry 等模块目录）。

  3. 发起验证

    工作区是鸿蒙工程根目录时，可以说：“使用 dt-verify 验证当前工程，Spec 在 /absolute/spec，按 Skill 完成计划、审查、执行和汇总。”工作区不是鸿蒙工程时，写出工程根目录：“使用 dt-verify 验证工程 /absolute/harmony-project，Spec 在 /absolute/spec……”，访问工作区外的路径时 DSH 可能请你授权。迁移场景再给出 Android 工程路径；需要修复时写明授权范围。

  4. 查看结果

    打开汇总文件，按验收项查看执行状态、验收结论、证据路径和剩余缺口。

理解结果的范围

只用于鸿蒙工程。插件装在 Profile 上，在任何工作区都能看到 dt-verify。被测路径（当前工作区，或请求里给出的路径）须是鸿蒙工程根目录；不是鸿蒙工程、或指到 entry 等模块目录时，准备阶段直接拒绝，提示在鸿蒙工程根目录下使用，不创建运行目录，也不改动任何文件。

未验证就是未验证。缺少环境、设备或依据的要求保持受阻或未验证，不会缩小验收范围。

验证只改测试文件。计划与执行阶段只在 ohosTest 下写测试；修改生产代码只发生在调用者授权的修复阶段。

环境要求不随宿主改变。UT/UI 结论需要真实的 SDK 与设备执行证据；UI 执行目前只在 macOS 上验收过。Harmony 构建会写入用户目录下的缓存，在 DSH 默认的工作区写入权限下可能需要逐次授权。

预览版。当前为开发候选版本，接口与行为可能随后续版本调整。

ECAT

把「降低代码熵」
配置成一条可执行的循环。

ECAT 用生成者与判别者的对抗循环改进代码。这个插件不替你写代码，它负责把循环配置好、跑起来， 并让你随时看到熵在往哪个方向变。

DSH 里用 /ecat-setup 完成配置，用 /ecat-refine 查看、启动和停止循环。

安装与首次准备

插件自带 ECAT 的 wheel 包与两个技能，不需要预先安装 ECAT，但首次配置会创建隔离环境并从网络拉取依赖。

  1. 在 DSH 插件市场添加索引源

    打开「插件」→ 展开「更多」→ 启用「自定义插件市场」→「发现」→「添加索引源」，填入市场地址后重新读取目录。

  2. 安装 ECAT 插件

    在市场里找到 ECAT 并安装。插件包的安装方式与同市场的其他包一致，安装后重新打开会话即可使用两个命令。

  3. 确认环境

    发送 /ecat-setup help，它会创建托管环境并逐项检查 ECAT 声明的每个运行时依赖，列出包名与版本。

    # 环境就绪时的典型输出
interpreter: ~/.dsh/ecat-venv/Scripts/python.exe
python: 3.11.13
environment: ready — all 13 runtime dependencies usable
  pydantic 2.14.1
  typer 0.27.3
  ...

两个命令

一个是配置，一个是运行。配置产生的文件全部可读、可改、可版本管理。

/ecat-setup

访谈式配置，产出 profile 与打分插件

  • 不带参数时开始访谈，先复用当前会话里已经说过的任务信息，只问真正缺的部分
  • 逐个维度确认判别方式：硬维度给命令，代理维度给判分规则，并确定权重与不适用时的处理
  • 把答案写成配置，并生成可直接运行的维度插件，不需要你手写 Python
  • 追加 help 只检查环境，不写入任何文件，也不启动访谈

/ecat-refine

查看运行状态、启动与停止循环

  • status：最近一轮的熵值、迭代次数和最差维度（默认）
  • open：在浏览器打开熵的可视化面板
  • preflight：只校验工作区配置，不启动任何东西
  • start / stop：后台启动与停止

一次完整的使用

从任务描述到第一次看到熵值，通常就是这几步。

步骤做什么你会得到
1发送 /ecat-setup，说清任务目标、目标目录和验收标准一份访谈结果，确认后才会落盘
2确认维度设计：判别方式、权重、不适用时怎么办ecat.config.yaml、profile 与可运行的维度插件
3把需要的技能与子代理放进工作区循环执行时可调用的能力
4发送 /ecat-refine start后台运行，返回运行目录
5发送 /ecat-refine status 或 /ecat-refine open熵值变化与最差维度

一轮的耗时由目标规模、维度数量和模型速度决定，从几分钟到几十分钟不等，所以循环在后台跑， 命令只负责查看和启停。

适合什么任务，不适合什么任务

ECAT 的价值来自「熵能被客观衡量」。任务能不能拆出可执行的判别方式，基本决定了它适不适合。

适合

  • 有客观判别标准的改进：构建必过、测试必过、静态检查、错误数量、接口契约。
  • 规模可控的局部重构：目录边界清楚，改动半径有限，失败回滚代价低。
  • 重复性质量问题：同一类坏味道反复出现，希望系统性收敛而不是逐处修。
  • 需要留下过程证据的任务：每轮改了哪里、熵降了多少，都能从运行目录里查到。

不适合

  • 没有可执行判据的任务：好坏只靠主观感觉，代理维度也给不出稳定结论。
  • 一次性的探索或原型：配置成本高于收益，直接写代码更快。
  • 跨多个仓库或需要外部系统配合的改动：循环只在自己配置的目标目录里工作。
  • 正确性尚未定义的新功能：先明确需求与验收标准，再考虑用循环去打磨。

边界与失败模式

这些是设计上的取舍，不是待修的缺陷。

需要 Python 3.11+

插件在首次配置时创建隔离环境并安装自带的 wheel。依赖从网络解析，所以第一次准备必须有可用的网络。

不替你判断业务正确性

熵下降说明代码在这组维度上更整齐，不代表功能符合预期。判据本身设计错了，循环会高效地朝错误方向优化。

只在自己配置的目录里工作

目标目录之外的改动不会被循环处理。跨仓库的约束需要写成一个显式的检查命令，否则不会被感知。

运行不会自动停下

循环在后台持续迭代，达到目标或你想收手时用 /ecat-refine stop 停止，避免持续消耗模型调用。

Crowd Memory v0.1.1

Coding Agent群体记忆

把一个 coding Agent 在开发任务中验证过的经验，提供给处理相关问题的其他 Agent，并保留来源、适用条件和测试结果。

终端 · 安装 Crowd Memory
dsh plugin --profile web add @fuxi-ailabs/crowdmemory-dsh-adapter@0.1.1

先启动本机 Runtime；web 换成实际使用的 DSH Profile。 安装步骤 ↓

功能演示安装使用

DSH 0.1.6-alpha.2 或 ^0.2.0-rc.2 · adapter/runtime 0.1.1

本机 Runtime · Node.js ≥ 22.18 · Python ≥ 3.10 使用条件 ↓

使用场景与适合人群

适合使用 coding Agent 的应用开发者

修复代码与接口问题

“其他 Agent 是否修过类似的代码问题？”

让 Agent 查阅已有的问题定位和修法，核对当前代码、依赖版本与接口行为，再补修改和回归测试。

适合开发 workflow 的集成与维护者

在开发 workflow 中传递经验

“上一次在构建或测试阶段遇到过什么问题？”

把构建、测试阶段留下的排查经验提供给同机后续运行的 Agent。需要按开发阶段采集时，使用 workflow-default。

适合维护构建与测试环境的开发者

复用构建排错方法

“相同的构建失败以前是怎么修好的？”

记录编译、依赖或配置问题的原因、实际命令和检查结果。后续 coding Agent 可核对记录，在当前项目重新验证修法。

同一后端问题，四个 Agent

GET 与 POST 共用一段 HTTP 处理代码，四个独立工作区遇到同类请求错误。上排先修复 GET，下排接手 POST。

  • 左上 A：独立定位和修复 GET，不写共享记忆。
  • 左下 B：在新工作区接手 POST，独立排查并补接口测试。
  • 右上 C：修复 GET 并测试后，用 memory_note 记录修法和适用条件。
  • 右下 D：用 memory_search、memory_read 读取 C 的记录，核对公共 HTTP 层，再修改 POST 并测试。

左列未安装记忆适配器，右列共享一个 Runtime。四个 Agent 的真实运行画面按阶段同屏整理，非同步计时；实际测试与来源读取回执见运行依据。

⌘ 在 DSH 中复现＋
发送给 DSH
在 CrowdMemory 的干净源码工作区中，检查 distributions/memory-runtime/src/crowdmemory_runtime/server.py：带协议头的 GET /v1/status 遇到 Content-Length: abc 时直接断连。先用真实 HTTP/Unix socket 测试复现，再修复为结构化 JSON 400，确认正常请求和过大请求的行为不回归。验证后记录实际经验；再让独立工作区的 Agent 读取记录，核对并修复 POST 入口，运行接口测试。确保 Python 3.11、pytest 和项目依赖已就绪，且实际导入当前工作区的源码。

宿主与插件
adapter/runtime 0.1.1；DSH 支持 0.1.6-alpha.2 或 ^0.2.0-rc.2，包含市场基准 0.2.1-rc.2。
独立安装
Runtime 本地 npm 安装，在指定目录建立独立 Python 环境；不需要全局安装 Runtime。
适用范围和限制 ＋
开发任务范围

本页示例与评测面向 coding Agent 的代码修复、构建排错、接口测试和开发 workflow，其他业务场景的适用性未经本页验证。本机共享与 workflow 可用，跨机器开发协作仍为内部预览；跨项目复用需核对 project/global 范围。

在当前项目重新验证

代码、依赖和运行环境变化后，原来的修法可能不再适用。Agent 采用前应核对条件，采用后运行当前项目的测试。记忆服务不可用时，开发会话继续执行，但这一步不带记忆。

配置与验证

DSH Profile 决定插件装在哪个环境，Runtime 的 session-default/workflow-default 是采集模板。实际连接取决于启动 DSH 的进程收到的端点配置。

  1. 1

    检查环境 确认 Node.js、Python 和 DSH 满足上面的条件。 终端

    node --version
python3 --version
dsh --version
  2. 2

    本地安装 Runtime 在独立目录安装 npm 包，Runtime 在 prefix 下建立隔离环境。 终端 A

    mkdir -p CMLocal && cd CMLocal
npm install --save-exact @fuxi-ailabs/crowdmemory-runtime@0.1.1
npx --no-install crowdmemory-runtime install --prefix "$PWD/.runtime/crowdmemory"
  3. 3

    启动记忆服务 保持前台终端运行；Ctrl-C 会停止服务。 终端 A · CMLocal

    npx --no-install crowdmemory-runtime start --prefix "$PWD/.runtime/crowdmemory"
  4. 4

    安装并连接 DSH 另开终端进入同一 CMLocal 目录，将端点传给 DSH。web 换成自己的 Profile。 终端 B · CMLocal

    export CROWDMEMORY_ENDPOINT_FILE="$PWD/.runtime/crowdmemory/state/endpoint.json"
dsh plugin --profile web add @fuxi-ailabs/crowdmemory-dsh-adapter@0.1.1
dsh --profile web
  5. 5

    检查状态并运行 coding 例子 另开终端检查状态。在 DSH 中运行上面的修复任务，写下经验后再启动独立 Agent，读取记录、修改代码并运行测试。 终端 C · CMLocal

    npx --no-install crowdmemory-runtime status --prefix "$PWD/.runtime/crowdmemory"
检查结果 ＋
  1. 检查环境

    Node.js ≥ 22.18，Python ≥ 3.10，DSH 位于支持范围。

  2. 本地安装 Runtime

    安装输出包含 Runtime 目录、Python 环境及 host-config.json。

  3. 启动记忆服务

    Runtime 启动，并生成 state/endpoint.json。

  4. 安装并连接 DSH

常见问题

开发经验如何提供给其他 coding Agent？＋

修复并完成测试后，让 Agent 用 memory_note 记录现象、原因、实际修法、适用条件和检查结果。后续会话在相关开发任务或失败出现时可收到记录与命中理由，也可用 memory_search、memory_read 查找和核对来源；采用后仍需在当前代码上验证。

已经有 session-default，为什么还要 DSH Profile？＋

DSH Profile 决定插件安装在哪个环境，例如 web；session-default / workflow-default 是 Runtime 的采集模板，两者不同。

必须全局安装吗？Node.js 18 可以吗？＋

不需要全局安装 Runtime，按上面的独立目录步骤操作即可。npm 发布包需要 Node.js ≥ 22.18；Node.js 18 不满足要求。

为什么另一个 Agent 没有收到记录？＋

检查两边是否连接同一 Runtime、记录的 project/global 范围和端点配置。笔记从后续会话开始可见，不推给写入它的同一会话。从 Dock 启动的桌面程序不会自动继承终端环境变量，需按配置文档设置。

如何判断已有修法适用于当前代码？＋

核对问题现象、源码位置、依赖版本、运行环境和记录中的适用条件，查看实际 diff 与验证结果，再在当前工作区运行回归测试。历史测试通过不保证当前修改正确。后端 API 录像和受控构建评测的范围及原始依据见评测与运行依据链接。

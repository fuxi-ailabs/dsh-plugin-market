workflow-rsi v0.1.0-alpha.1

ToD 静态工作流递归自我改进

面向 ToD（to Developer，面向开发者）的静态工作流做递归自我改进：不改模型权重，用真实运行结果诊断问题、生成改动并在整个 Workflow 上评测，以 PR 交付更好的版本。

终端 · 安装 workflow-rsi 操作台
dsh plugin --profile web add @fuxi-ailabs/workflow-rsi-dsh-console@0.1.0-alpha.1

先安装并启动 wrsi-server；web 换成操作台使用的 DSH Profile。 安装步骤 ↓

功能演示安装使用

DSH 0.1.6-alpha.2 或 ^0.2.1-rc.2 · 操作台与本体 0.1.0-alpha.1

wrsi-server 本机服务 · Node.js ≥ 22.19 · macOS 或 Linux 使用条件 ↓

使用场景与适合人群

适合维护 ToD 多阶段 Workflow 的工程师

Run 停下后定位并修复

“Run 停在第 5 个阶段，是输入的问题还是 Workflow 的缺陷？”

闭环读取停止证据，沿 Workflow 结构回溯，区分结构问题和节点内容问题，生成带测试的改动，验证通过后提出 PR；把握不足时停下交给人决定。

适合只能通过 API 调用模型的团队

不训练模型，持续提升效果

“拿不到模型权重，怎样让同一类任务越做越好？”

改动落在 Workflow 上，改好一次，之后同类任务都复用；每次尝试记成 Trial，按收益在改进方法之间分配预算。换模型后，固化在 Workflow 代码和测试里的判断可以直接复用。

适合Workflow 仓维护者与评审者

审一个带证据的改动

“这个 PR 改了什么，证据够不够合入？”

每个 PR 都附诊断结论、改动范围、测试和分级验证结果。合入由 Workflow 仓决定；合入后 workflow-rsi 重跑原任务，跟踪改动是否被保留。

改进对象与一次真实闭环

先说明 workflow-rsi 改进的是什么样的 Workflow，再看一个已接入的多阶段 Workflow 在同一份输入上的两轮。事件取自闭环账本，时间为 UTC，诊断一行依次为处理方式、所属层、置信度。

什么是静态工作流

静态工作流是结构随版本固定的 Workflow：有哪些阶段和节点、节点之间交接什么、在哪里分支、重试和设门禁，都写在 Workflow 仓的源码里；同一个版本对每个输入都按同一张结构图执行。每个节点用的模型、提示、Skill 和工具也随版本固定。运行时由 Agent 按输入临时决定步骤的编排属于动态工作流，不在 workflow-rsi 的改进范围内。

为什么只针对 ToD

ToD 即 to Developer：workflow-rsi 改进的是面向开发者、替开发者完成开发任务的静态工作流，例如从需求、分析、设计、计划到实现、构建与验证按固定阶段推进的工作流。这类工作流每个阶段都有可以自动判定的结果（构建是否通过、测试通过多少、覆盖率多少），能给出可重复的评测信号；改动可以用测试证明、以 PR 交付、合入后重跑同一任务复核。面向 ToB、ToC 业务的工作流，例如客服对话、业务审批、数据处理，暂不作为改进对象。

一个 ToD 静态工作流的结构

阶段与交接（示例中的 Workflow）
generate      准备任务与需求说明
  ↓
analysis      分析代码与依赖
  ↓
design        设计改动方案
  ↓
plan          拆成可执行的步骤
  ↓
execution     实现与构建
  ↓
verification  运行测试；失败时由 Repair 决定去向
                safe_fix          → 有限修复后复测
                request_redesign  → 交给 Redesign 重新设计
                no_action         → 结束（no_safe_repair）

workflow-rsi 在这张结构图上能改什么

  • 结构：插入已审步骤、删除可选步骤、调整允许的交接、切换已审策略；门禁和受保护路径不能动。
  • 节点内容：指令、Skill、工具说明和模型选择，经 skill / agent RSI 接口改进。
  • 两类改动都在整个 Workflow 上分级评测，产出的是一个新的静态版本，以 PR 交付。

第 1 轮在第 5 个阶段停下，报“输入无法准备”。workflow-rsi 确认输入本身合法，问题出在节点的输入检查规则；中间三次停下等人（两次把握不足，一次诊断 Agent 自身失败），人确认后继续。第四次诊断置信度 0.9，随后在独立分支生成 45 行改动和测试，L1、L2 通过后提出 PR，PR 合入。从 Run 停下到提出 PR 用时 4 小时 8 分钟，其中等人 14 分钟；模型用量约 3113 万 token，其中 2908 万为缓存命中。

PR 合入后同一份输入再跑，Run 越过了原来的停止点，停在同一阶段的后一个节点。诊断指出这个节点只支持一种处理方式；第一次修复超时没有改动，第二次改动没有给出测试命令和改动说明，没有通过改动范围检查。workflow-rsi 不提 PR，把诊断结论留给人决定。

结构问题：补上阶段之间的交接

Repair 角色任务说明 · 改动前后
改动前
Apply one bounded safe fix, request Redesign, or report that
no safe action exists from frozen verification evidence.

改动后
From frozen verification evidence, apply one bounded safe fix
(safe_fix), or choose request_redesign, the only route to
Redesign: use it when no bounded safe fix exists but a redesign
could address the failure. no_action ends Verification with
no_safe_repair; choose it only when neither a safe fix nor a
redesign can address the failure.

另一次运行停在最后一个阶段：修复角色选择“不处理”之后流程没有出口，以修复预算耗尽结束。诊断定位到任务说明没有写清三种决定各自的去向，属于阶段之间的交接问题。修复只改了一句话并加了一条测试；再跑时，修复角色要求重新设计，流程正确交给了重新设计角色。

在 DSH 操作台里查看闭环并给出决定

发送给 DSH
/wrsi loop <loop id>
/wrsi loop-resume <loop id> fix --confirm

闭环停下时人可以给出的决定

  • fix：重新诊断，再生成修复候选。
  • rerun：不改动，重跑 Workflow，例如环境恢复之后。
  • give-up：结束这个闭环。
  • merge-done：PR 已在 Workflow 仓合入，开始重跑。
  • 写命令不带 --confirm 时只显示将要执行的操作，不执行。

事件为真实闭环账本的原始记录，按时间排版。

被改进的 Workflow
ToD（面向开发者）的静态工作流，需要它的适配器读取 Run 的状态和停止记录，以及仓库与闭环配置

workflow-rsi 由本体和 DSH 操作台两个 npm 包组成。判定、状态与注册表都不进 DSH 进程，插件只经 wrsi-server 的本机 HTTP API 和 wie 子进程访问它。

适用范围和限制 ＋
改进对象

ToD（to Developer，面向开发者）的静态工作流：需求、分析、设计、计划、实现、构建、验证等阶段按固定结构推进，结构随版本固定，每个阶段有可自动判定的结果。运行时按输入临时编排步骤的动态工作流，以及面向 ToB、ToC 业务的工作流，不在改进范围内。

适合的场景

同一个静态工作流反复处理同类开发任务、由多个阶段和 Agent 组成、团队要求改动可审计可回滚。只跑一次的任务，或者 Workflow 还没有接入适配器时，用处不大。

操作台的范围

操作台在 DSH 里查看会话、Run、停止记录、闭环和工作计划，并转交人的决定。11 个工具都只读，守卫拒绝其他 wrsi_ 写工具；诊断、评测、提出 PR 和闭环都由 workflow-rsi 本体完成。

由人准入

评分规则、发布标准、预算分配和新改进方法的启用只由人准入，workflow-rsi 和 Agent 都改不了；是否合入 PR 由 Workflow 仓的维护者决定。Harness（会话、沙箱、预算、状态、证据）不自动修改。

  1. 1

    安装 workflow-rsi 本体 全局安装后得到 wie 与 wrsi-server 两个命令；包内自带内部库，只另外从 registry 安装 TypeScript。 终端

    npm install -g @fuxi-ailabs/workflow-rsi@0.1.0-alpha.1
which wie wrsi-server
  2. 2

    启动 wrsi-server 按使用文档写一个最小 wie.config.json（业务名、actor、registry_root、server.data_root 与 server.key_file，路径放在工作目录之外），然后在前台启动服务。 终端 A · 保持运行

    wrsi-server --config /abs/path/wie.config.json --port 8799
  3. 3

    安装操作台插件 建议给操作台单独建一个 Profile，只放这一个插件；web 换成实际使用的 Profile。桌面版也可在「插件」→「发现」中找到 workflow-rsi 操作台安装。 终端 B

    dsh plugin --profile web add @fuxi-ailabs/workflow-rsi-dsh-console@0.1.0-alpha.1
  4. 4

    配置 key 与 wie 在该 Profile 的 cordis.patch.yml 里写上服务地址、key 文件和 wie；未知字段在插件加载时报错。 cordis.patch.yml

    - id: wrsi-console
  config:
    server_url: http://127.0.0.1:8799
    key_file: /abs/path/wrsi-server.key
    wie: { argv: [wie], config: /abs/path/wie.config.json }
    timeout_ms: 30000
  5. 5

    验证连通并查看闭环 在操作台 Profile 里发送命令；也可以直接问 Agent “workflow-rsi 现在有哪些会话”，它会调用 wrsi_sessions。 发送给 DSH

    /wrsi status
/wrsi loop

    输出 wie 与 wrsi-server 的路径。

  2. 启动 wrsi-server

常见问题

什么是静态工作流？＋

结构随版本固定的 Workflow：阶段、节点、交接、分支、重试和门禁写在 Workflow 仓的源码里，同一个版本对每个输入都按同一张结构图执行，节点用的模型、提示、Skill 和工具也随版本固定。workflow-rsi 每次改进产出一个新的静态版本，经评测后以 PR 交付。

我的工作流不是面向开发者的，能用吗？＋

workflow-rsi 只针对 ToD（to Developer，面向开发者）的静态工作流，依赖构建、测试、覆盖率这类可以自动判定的阶段结果做评测。面向 ToB、ToC 业务的工作流暂不支持；运行时按输入临时编排步骤的动态工作流，也不在改进范围内。

workflow-rsi 和直接改提示词或 Skill 有什么区别？＋

workflow-rsi 先沿 Workflow 结构诊断，再决定改哪里：结构问题用已审批的结构算子和受约束搜索生成候选，节点内容（指令、Skill、工具说明、模型选择）交给 skill / agent RSI 接口。两类改动都在整个 Workflow 上分级评测，局部得分只作参考，以 PR 交付。

操作台会自己改 Workflow 或合入 PR 吗？＋

不会。操作台注册 11 个只读工具和一个 /wrsi 命令，Agent 无法经工具改动 workflow-rsi。admit、publish、loop-resume、plan-decide 这类写命令必须由人带上 --confirm 才执行；PR 是否合入由 Workflow 仓的维护者决定。

闭环停下等人时怎么处理？＋

诊断把握不足、候选验证不过、环境故障等情况都会停下。用 /wrsi loop <loop id> 查看停止原因和诊断结论，再用 /wrsi loop-resume <loop id> <fix|rerun|give-up|merge-done> --confirm 给出决定。

接入一个新的 Workflow 需要准备什么？＋

需要该 Workflow 的适配器，用来读取 Run 的状态和停止记录、输出事实；适配器不下结论。另外配置 Workflow 仓库与闭环配置，以及人准入的评测资产。

插件调用失败，先检查哪里？＋

先确认 wrsi-server 在运行、server_url 正确、key_file 可读且与服务一致；闭环与工作计划功能还需要配置 wie。各种情况的返回见“错误与写操作”文档。插件不重试，也不在不可用时猜测结果。

评分规则和发布标准由谁来定？＋

只由人准入。workflow-rsi 和 Agent 都改不了评分规则、发布标准和预算分配；新的改进方法由 method-author 提出，经影子试验和人工准入后启用。

workflow-rsi

workflow-rsi 以评测结果驱动 Workflow 的修改。改动有三个来源：人提出的请求、按产品需求排出的工作计划，以及 Run 停下后的闭环诊断。每个改动都用人准入的评测资产判定，以 PR 交付；是否合入由 Workflow 所在的仓决定，合入后再验收一次。

每次尝试都记成一条 Trial：起因、改动、评测结论、合入后是否还在。哪种改进方法更有效、预算投向哪里，都按这些记录计算。人负责准入评测规则、审 PR，以及处理需要人决定的情况。

有什么用#

一个改动从提出到落地：

text
改动来源
  请求：人描述要改什么
  工作计划：产品需求拆成需求集，逐条发起请求
  闭环：Run 停下，按停止证据诊断
  ↓
改动：人在自己的目录里改（workflow-rsi 只读快照），或由 agent 在独立 worktree 里改
  ↓
评测：人准入的测试、judge 与判定规则（不通过 → 等人）
  ↓
PR：正文带评测结论，人审、合入
  ↓
合入后验收：同一份输入重跑，或在目标分支上重跑冻结的测试
  ↓
Trial 记录：起因、改动、评测结论、是否落地
能力说明
三种改动来源请求：人描述要改什么，自己改或交给 agent 改；工作计划：产品需求拆成需求集，逐条发起请求；闭环：Run 停下后按停止证据诊断、生成修复
以评测判定改动测试、judge 与判定规则都是评测资产，只由人准入；被评测的改动不能修改评测工具本身；配置了 validation 与 holdout 时，validation 选候选，holdout 决定能否发布
隔离修改，以 PR 交付agent 的改动在独立 worktree 和操作系统沙箱里完成；人在自己目录里的改动，workflow-rsi 只读快照；PR 正文带评测结论，合入由 Workflow 仓决定
合入后再验收闭环用同一份输入重跑，看是否越过原停止点；工作计划在目标分支上重跑冻结的独立测试，通过才算完成
全程可以回查每次尝试都是一条 Trial；wie report rsi 按工程、业务、递归三栏汇总，DSH 操作台也能查看

什么时候用#

场景得到什么
同一个 Workflow 反复处理同类任务每次停止都落到 Workflow 本身的修复上，后面的任务一起受益
产品需求变了，Workflow 要跟着改需求拆成一条条请求，每条带冻结的验收测试，合入后在目标分支上验收
Workflow 由多个阶段、多个 Agent 组成，经常停在中间某一步停在哪一步、为什么停的结构化记录，以及对应的修复 PR
团队要求 Workflow 的每个改动都经过评审、可以回退每个改动都是带测试和验证结果的 PR，合入由 Workflow 仓决定

只跑一次的任务，或者 Workflow 还没有接入 workflow-rsi 时，用处不大。接入一个 Workflow 需要它的适配器，用来读取 Run 的状态和停止记录。

用上后的收益#

Workflow 的改进从“人看日志、想办法、改代码、再跑一遍”，变成审一个带证据和评测结论的 PR。下面是闭环入口在一个已接入的多阶段 Workflow、同一份输入上的两轮：

轮次停在哪里workflow-rsi 做了什么，结果如何
第 1 轮第 5 个阶段的一个节点，在处理输入之前定位到节点的输入检查过严，把一种合法输入判为无法处理；生成 45 行改动并附测试，测试通过后提出 PR，PR 合入。从 Run 停下到提出 PR 用时 4 小时 8 分钟，其中等人 14 分钟
第 2 轮同一份输入重跑，越过第 1 轮的停止点，停在同一阶段的后一个节点定位到这个节点只支持一种处理方式，不覆盖这份输入；第一次修复超时没有改动，第二次改动没有通过改动范围检查，不提 PR，停下交给人

这是一个 Workflow、一份输入上的实测，还没有做多 Workflow 统计。第 1 轮的模型用量约 3113 万 token，其中 2908 万为缓存命中。诊断也会出错：在另一次运行中，诊断把原因归到了错误的节点，由人纠正后修复。

例子#

下面三个例子都来自闭环入口。

一次完整的闭环。第一轮 Run 前四个阶段通过，在第五个阶段停下，报“输入无法准备”。workflow-rsi 读取停止证据后确认，这份输入本身合法，问题出在节点的输入检查规则。中间诊断三次停下等人：两次把握不足，一次诊断 Agent 自身失败，人确认后继续。第四次诊断的置信度为 0.9，随后在独立分支上生成改动和测试，验证通过后提出 PR。这一轮的事件记录（时间为 UTC，诊断一行依次为处理方式、所属层、置信度）：

18:45  loop.escalated    diagnosis_low_confidence
18:47  loop.resumed      fix
21:07  loop.escalated    agent_failed

验证不过就不提交。PR 合入后，同一份输入再跑，Run 越过了原来的停止点，停在同一阶段的后一个节点。诊断指出这个节点只支持一种处理方式（置信度 0.82）。第一次修复 Agent 用完 90 分钟没有产出改动；第二次改了 4 个文件、133 行，但没有给出测试命令和改动说明，没有通过改动范围检查。workflow-rsi 没有提出 PR，停下来把诊断结论留给人决定。第 2 轮的事件记录（节选）：

10:03  triage.decided    diagnose

                         scope: the fix agent named no test_command

定位阶段之间的交接缺口。另一次运行停在最后一个阶段：修复角色（Repair）选择“不处理”之后，流程没有出口，以修复预算耗尽结束。诊断定位到这个角色的任务说明没有写清三种决定各自的去向，这是阶段之间的交接问题，角色本身的能力没有问题。修复只改了任务说明的一句话，并加了一条测试；再跑时，修复角色要求重新设计，流程正确交给了重新设计角色（Redesign）：

text
改动前
Apply one bounded safe fix, request Redesign, or report that
no safe action exists from frozen verification evidence.

改动后
From frozen verification evidence, apply one bounded safe fix
(safe_fix), or choose request_redesign, the only route to
Redesign: use it when no bounded safe fix exists but a redesign
could address the failure. no_action ends Verification with
no_safe_repair; choose it only when neither a safe fix nor a
redesign can address the failure.

人和 workflow-rsi 各做什么#

事项由谁来做
评测改动、提出 PR、合入后验收、记录 Trialworkflow-rsi
闭环中的运行、诊断与生成修复workflow-rsi 调用的 agent，在沙箱里运行
请求中的改动人自己改，或交给 workflow-rsi 托管的 agent
是否合入 PRWorkflow 仓的维护者
诊断把握不足、候选验证不过、环境故障等停止人在 DSH 操作台或 wie 里决定继续、重试或结束
评测资产与判定规则：什么算通过、什么时候停、改进方法与预算怎么分只由人准入，workflow-rsi 和 agent 都改不了

市场收录的是 workflow-rsi 的 DSH 操作台：在 DSH 里查看会话、Run、停止记录、闭环和工作计划，需要人决定的操作由人执行。例如查看一个闭环，再让停下的闭环继续修复：

text
/wrsi loop <loop id>
/wrsi loop-resume <loop id> fix --confirm
决定含义
fix重新诊断，再生成修复候选
rerun不改动，重跑 Workflow，例如环境恢复之后
give-up结束这个闭环
merge-donePR 已在 Workflow 仓合入，开始重跑

写命令不带 --confirm 时只显示将要执行的操作，不执行。评测、提出 PR 和闭环都由 workflow-rsi 本体完成，操作台只查看和转交人的决定。

安装 workflow-rsi 本体#

workflow-rsi 由本体和 DSH 操作台两个 npm 包组成：

项值
插件@fuxi-ailabs/workflow-rsi-dsh-console 0.1.0-alpha.1
workflow-rsi 本体@fuxi-ailabs/workflow-rsi 0.1.0-alpha.1（命令 wie、wrsi-server）
DSH0.1.6-alpha.2 || ^0.2.1-rc.2 (1)
系统macOS 或 Linux，Node.js ≥ 22.19

(1) 已在 0.1.6-alpha.2 与 0.2.1-rc.2 上实跑验收，详见组件与版本。

注意

workflow-rsi 的判定、状态与注册表都不进 DSH 进程。插件只经 wrsi-server 的本机 HTTP API 和 wie 子进程访问它，不启动、不重启服务。运行闭环还需要被改进 Workflow 的适配器、仓库与闭环配置。

bash
npm install -g @fuxi-ailabs/workflow-rsi
which wie wrsi-server

包内自带 workflow-rsi 的内部库，只另外从 registry 安装 TypeScript（用于符号级的改动范围检查）。

启动服务#

写一个最小配置 wie.config.json，路径都放在工作目录之外：

json
{
  "business": "<业务名>",
  "actor": "<你的 id>",
  "registry_root": "/abs/path/registry",
  "server": { "data_root": "/abs/path/wrsi-server", "key_file": "/abs/path/wrsi-server.key" }
}
bash
wrsi-server --config /abs/path/wie.config.json --port 8799

key_file 不存在时服务首次启动会生成它（权限 0600），之后重启沿用同一个 key。服务只监听本机，API 请求都要带这个 key。

安装插件#

桌面版：打开「插件」→「发现」，在 Fuxi DSH 插件市场中找到 workflow-rsi 操作台，点击安装。

命令行：

bash
dsh plugin --profile <profile> add @fuxi-ailabs/workflow-rsi-dsh-console

建议给操作台单独建一个 profile（例如 dsh wrsi-console --from-default-profile web --dump-config），只放这一个插件。

配置#

在该 profile 的 cordis.patch.yml 里写上 key 与 wie：

yaml
- id: wrsi-console
  config:
    server_url: http://127.0.0.1:8799
    key_file: /abs/path/wrsi-server.key
    wie: { argv: [wie], config: /abs/path/wie.config.json }
    timeout_ms: 30000
配置含义默认
server_urlwrsi-server 的 http(s) origin127.0.0.1:8799（http）
key_filewrsi-server 的 key 文件绝对路径（可写 ~/…）无；不配时 HTTP 类功能不可用
wie.argv / wie.configwie 命令前缀与它的配置文件无；不配时闭环与工作计划功能不可用
timeout_ms单次 HTTP 请求或 wie 子进程的超时30000

未知字段在插件加载时报错。key 每次请求时从文件读，只放进请求头，输出里出现时替换为 <key>。

验证#

在操作台 profile 里输入：

text
/wrsi status

返回业务名、actor 与服务状态即为连通。也可以直接问 Agent「workflow-rsi 现在有哪些会话」，它会调用 wrsi_sessions。服务没启动时插件不影响会话，工具返回 available: false 与原因，见错误与写操作。

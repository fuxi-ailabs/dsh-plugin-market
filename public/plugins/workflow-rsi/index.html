workflow-rsi

workflow-rsi 让 Workflow 根据自己的运行结果持续改进。给它一个任务，例如一个库名和版本，它运行 Workflow；Run 停下后，它按停止证据定位原因，对能修的问题生成改动、验证通过后以 PR 提交到 Workflow 所在的仓；PR 合入后，用同一份输入重跑，检查是否越过了原来的停止点。

找问题、写改动、验证、重跑都由 workflow-rsi 完成，人负责审 PR，以及处理它判断需要人决定的停止。每一轮为什么停、改了什么、验证结果如何，都有记录可以回查。

有什么用#

能力说明
从停止证据定位问题记录 Run 停在哪个阶段、哪个节点、什么错误，按停止类型决定继续、诊断或交给人；诊断给出根因、所属层和置信度
改动先验证再提交修复候选在独立分支上生成，先检查改动范围，再跑测试，通过后才提出 PR；验证不过就不提交
用同一份输入检验效果PR 合入后，用同一个库、同一个版本、同一份源码重跑，看问题是否真正解决
人只在需要的时候介入诊断把握不足、候选验证不过、环境故障时停下等人；它不会自己合入 PR
全程可以回查停止记录、诊断结论、改动、验证结果、PR 与模型用量都保存下来，可在 DSH 操作台或 wie 中查看

什么时候用#

场景得到什么
同一个 Workflow 要处理一批同类任务，例如一批库的迁移每次停止都落到 Workflow 本身的修复上，后面的任务一起受益
Workflow 由多个阶段、多个 Agent 组成，经常停在中间某一步停在哪一步、为什么停的结构化记录，以及对应的修复 PR
团队要求 Workflow 的每个改动都经过评审、可以回退每个改动都是带测试和验证结果的 PR，合入由 Workflow 仓决定

只跑一次的任务，或者还没有为 Workflow 准备适配器时，用处不大。

用上后的收益#

Workflow 的改进从“人看日志、想办法、改代码、再跑一遍”，变成审一个带证据和测试的 PR。下面是在鸿蒙 PC 真机上，用库迁移 Workflow 处理 memray 1.20.0 的两轮闭环：

轮次停在哪里workflow-rsi 做了什么，结果如何
第 1 轮execution 阶段准备源码时，源码里有一个上游的符号链接定位到引擎把符号链接一律判为不可准备；生成 45 行改动并附测试，L1、L2 测试通过后提出 PR，PR 合入
第 2 轮同一份源码重跑，越过第 1 轮的停止点，停在 execution 阶段的构建定位到构建路由只支持 setuptools，而该库用 scikit-build-core；两次修复候选都没有通过验证，不提 PR，停下交给人

这是一个 Workflow、一个库上的实测，还没有做多库统计。诊断也会出错：在另一个库上，诊断曾把测试插件没有加载归到错误的原因，由人纠正后修复。

例子#

一次完整的闭环。memray 1.20.0 的第一轮 Run 在 execution 阶段停下，报“源码树里有符号链接，无法准备”。workflow-rsi 读取停止证据后确认，这个链接是上游仓库本来就有的，复制时解引用即可，问题出在引擎的源码准备规则。它在独立分支上改了源码准备逻辑并补上测试，检查改动范围、跑完测试后提出 PR。这一轮中，诊断曾三次因为把握不足停下等人，人处理后恢复，最后一次诊断的置信度为 0.9。PR 合入后，同一份源码再跑，Run 越过了原来的停止点。

验证不过就不提交。第二轮停在构建：该库用 scikit-build-core 构建，而引擎的构建路由只支持 setuptools，修复 Agent 两轮都在改构建文件，无效。workflow-rsi 的诊断指出了这一点（置信度 0.82），但两次修复候选都没有通过验证，它没有提出 PR，停下来把诊断结论留给人决定。

定位 Workflow 的交接缺口。处理 usearch 时，Run 停在 verification 阶段：Repair 角色选择“不处理”之后，流程没有出口，以修复预算耗尽结束。诊断定位到 Repair 的任务说明没有写清“不处理即终止、要求重新设计才进入 Redesign”，这是阶段之间的交接问题，Repair 的修复能力本身没有问题。按诊断修复后再跑，Repair 要求重新设计时正确进入了 Redesign。

人和 workflow-rsi 各做什么#

事项由谁来做
运行、记录停止、诊断、生成并验证改动、提出 PR、合入后重跑workflow-rsi
是否合入 PRWorkflow 仓的维护者
诊断把握不足、候选验证不过、环境故障等停止人在 DSH 操作台或 wie 里决定继续、重试或结束
判定规则：什么算通过、什么时候停、预算怎么分只由人修改，workflow-rsi 和 Agent 都改不了

市场收录的是 workflow-rsi 的 DSH 操作台：在 DSH 里查看会话、Run、停止记录、闭环和工作计划，需要人决定的操作由人用 /wrsi … --confirm 执行。运行、诊断、验证和提出 PR 由 workflow-rsi 本体完成。

安装 workflow-rsi 本体#

workflow-rsi 由本体和 DSH 操作台两个 npm 包组成：

项值
插件@fuxi-ailabs/workflow-rsi-dsh-console 0.1.0-alpha.1
workflow-rsi 本体@fuxi-ailabs/workflow-rsi 0.1.0-alpha.1（命令 wie、wrsi-server）
DSH0.1.6-alpha.2 || ^0.2.1-rc.2 (1)
系统macOS 或 Linux，Node.js ≥ 22.19

(1) 已在 0.1.6-alpha.2 与 0.2.1-rc.2 上实跑验收，详见组件与版本。

注意

workflow-rsi 的判定、状态与注册表都不进 DSH 进程。插件只经 wrsi-server 的本机 HTTP API 和 wie 子进程访问它，不启动、不重启服务。运行闭环还需要对应 Workflow 的适配器、仓库与闭环配置。

bash
npm install -g @fuxi-ailabs/workflow-rsi
which wie wrsi-server

包内自带 workflow-rsi 的内部库，只另外从 registry 安装 TypeScript（用于符号级的改动范围检查）。

启动服务#

写一个最小配置 wie.config.json，路径都放在工作目录之外：

json
{
  "business": "<业务名>",
  "actor": "<你的 id>",
  "registry_root": "/abs/path/registry",
  "server": { "data_root": "/abs/path/wrsi-server", "key_file": "/abs/path/wrsi-server.key" }
}
bash
wrsi-server --config /abs/path/wie.config.json --port 8799

key_file 不存在时服务首次启动会生成它（权限 0600），之后重启沿用同一个 key。服务只监听本机，API 请求都要带这个 key。

安装插件#

桌面版：打开「插件」→「发现」，在 Fuxi DSH 插件市场中找到 workflow-rsi 操作台，点击安装。

命令行：

bash
dsh plugin --profile <profile> add @fuxi-ailabs/workflow-rsi-dsh-console

建议给操作台单独建一个 profile（例如 dsh wrsi-console --from-default-profile web --dump-config），只放这一个插件。

配置#

在该 profile 的 cordis.patch.yml 里写上 key 与 wie：

yaml
- id: wrsi-console
  config:
    server_url: http://127.0.0.1:8799
    key_file: /abs/path/wrsi-server.key
    wie: { argv: [wie], config: /abs/path/wie.config.json }
    timeout_ms: 30000
配置含义默认
server_urlwrsi-server 的 http(s) origin127.0.0.1:8799（http）
key_filewrsi-server 的 key 文件绝对路径（可写 ~/…）无；不配时 HTTP 类功能不可用
wie.argv / wie.configwie 命令前缀与它的配置文件无；不配时闭环与工作计划功能不可用
timeout_ms单次 HTTP 请求或 wie 子进程的超时30000

未知字段在插件加载时报错。key 每次请求时从文件读，只放进请求头，输出里出现时替换为 <key>。

验证#

在操作台 profile 里输入：

text
/wrsi status

返回业务名、actor 与服务状态即为连通。也可以直接问 Agent「workflow-rsi 现在有哪些会话」，它会调用 wrsi_sessions。服务没启动时插件不影响会话，工具返回 available: false 与原因，见错误与写操作。

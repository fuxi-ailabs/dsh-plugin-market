# AgentLineage 开箱即用安装设计

日期：2026-10-26。2026-10-27 实施：Windows x64 完整运行包、状态与恢复面板、同源 Viewer；发布记录见本仓库安装验收文档。

用户在 DSH 网页点击一次「安装」，插件自动安装所需组件、启动本地服务并检查功能，最后显示「已就绪」。用户无需另外安装 Python 或 Core，无需填写解释器路径、端口、环境变量，也无需从特定终端重新启动 DSH。运行依赖安装在运行 DSH 的主机上；通过远程浏览器访问时，安装目标仍是 DSH 服务端主机。

首版采用**插件随附 Windows x64 完整 Core 运行包**，保留现有 DSH 功能。运行包包含隔离的 Python 运行时、匹配版本的 Core、第三方依赖和 Viewer 静态资源。用户只看见 AgentLineage 这个插件，运行包由包管理器随插件安装。

## 实施时的分发选择

项目要求保持私有分发，alpha.4 沿用已有的 GitHub Git 来源和私有 Release，将固定摘要的 Windows 运行包直接随插件分发。没有新增 npm 发布或登录要求。Git 来源仍需要 DSH 已有的 Git 工具与仓库访问权限；完全不依赖 Git 的分发通道不在本次发布承诺中。其他平台的独立运行包及通用 DSH readiness 协议保留为后续设计。现有 DSH 插槽与认证 Connection 已用于实现本插件的状态、恢复和 Viewer 接入。

## 原问题

市场当前提供 `@fuxi-ailabs/dsh-agentlineage@0.1.0-alpha.3`，固定来源为 `bf28b828710f1c146895bdfb63108934edbd1fe5`。该版本默认使用 `managed` 模式，但只管理 Core 的启动与停止，没有分发 Python 和 Core。本机默认 Python 3.12.10 可以运行，查找 `agentlineage_core` 返回空；实际 DSH 网页显示组件「异常」。

`runtime.ts` 在插件启用时执行 `python -m agentlineage_core.cli`，等待服务地址，再注册工具。子进程提前退出时，只报告泛化的英文 Core 启动失败，缺少依赖与目录占用共用一条提示。市场卡片没有说明这项额外安装要求，介绍页才提供手动准备步骤。

这次问题需要同时调整运行包分发、插件启动行为和安装界面的成功判定。仅改市场介绍页不能实现开箱即用。

## 用户操作

正常安装流程为：

```text
安装 AgentLineage
    ↓
安装插件和适合当前主机的运行包
    ↓
检查文件完整性与运行条件
    ↓
启动本地分析服务
    ↓
确认 DSH 功能可用
    ↓
已就绪 → 开始使用
```

「安装」按钮旁说明：首次安装会同时安装本地分析组件，完成后自动启动。下载大小应来自发布元数据；未取得可靠大小时只显示阶段，不展示估算百分比或固定等待时间。

安装中的网页可以关闭。DSH 主机继续执行任务，再次打开页面时读取该次安装状态。点「取消」才取消安装；进入不可中断的激活阶段时，说明「正在完成配置，完成后可停用」，遵循 DSH 已有取消语义。

插件停用后显示「已停用」；再次启用直接使用已经安装的运行包。日常启动不下载依赖。自动重试只处理可恢复的短暂失败，不能在后台无限下载或重启。

## 运行包分发

建议下一插件版本为 `0.1.0-alpha.4`，实际版本在发布时确定。以下包名与版本均为拟议配置：

```text
@fuxi-ailabs/dsh-agentlineage
  dist/                   已构建的插件与启动管理代码
  cordis.patch.yml        默认 managed，自动选择随包运行时
  locale/                 页面与错误文案
  optionalDependencies
    @fuxi-ailabs/agentlineage-runtime-win32-x64
    @fuxi-ailabs/agentlineage-runtime-darwin-arm64
    @fuxi-ailabs/agentlineage-runtime-darwin-x64
    @fuxi-ailabs/agentlineage-runtime-linux-x64
```

各运行包通过 `os`、`cpu` 声明平台，固定精确依赖版本。包管理器按 DSH 主机平台选择安装；平台可选依赖安装失败或被跳过时，插件必须识别「运行包缺失」，不能据插件目录存在便宣布可用。Linux 还需声明并检查 libc 与最低版本，不能只按 `linux/x64` 判定兼容。未验证的平台明确显示暂不支持。

首个交付平台是当前使用的 Windows x64。其他平台通过对应的打包与安装验证后再加入支持矩阵；发布入口不能把尚未验证的平台列为已支持。

运行包使用独立目录中的解释器和已安装模块，以绝对路径启动；不查找系统 Python、不调用系统 pip、不写全局 PATH。Windows 首版优先采用随包解释器加预安装模块的目录布局；发布构建必须验证解释器隔离和所有运行依赖。macOS 与 Linux 使用各自可分发的运行环境，并按平台要求完成签名或兼容性验证。具体文件布局以最终包在干净主机上的运行结果为准。

每个包附运行清单，记录平台、架构、最低系统条件、插件协议版本、Core 版本、功能集合和文件摘要。包管理器校验包完整性，启动前校验包内文件，并以实际能力检查确认兼容性。摘要不能替代发布来源校验。

所有依赖在发布时预构建。安装路径不依赖 `postinstall`、现场编译、`pip install` 或 Git 检出。DSH 当前会单独管理依赖构建脚本授权，预构建分发可以直接通过现有包安装流程，无需用户额外允许构建脚本。离线交付提供包含所需平台依赖的完整安装材料；只拷贝主插件 tarball 不算完整离线包。

## 插件启动与生命周期

把当前「连接 Core 完成后才初始化插件」拆成常驻的管理入口和可重建的运行实例。管理入口先提供状态、重试与诊断，再启动 Core。准备过程中不向 Agent 暴露尚不可用的分析工具；服务就绪后注册工具，服务退出后撤销或明确阻止调用，并更新状态。

默认配置只保留 `mode: managed`。启动管理器定位随包运行环境，以绝对路径启动 Core，由当前 Profile 管理子进程；自动分配 loopback 端口，完成能力握手后才标记 `ready`。至少核对 `dsh-native-v4`，并检查本版七个工具实际依赖的接口。

继续支持 `external` 模式，放在高级配置中。外部服务由部署方管理生命周期，停用插件不会终止它。用户显式配置的旧 `pythonPath` 也不静默覆盖；升级后提供「切换到内置运行环境」，默认新安装使用随包环境。

多个 Profile 可以共享只读运行包，各自持有数据目录和所属 Core。停用、卸载或 DSH 正常退出时终止所属子进程；异常退出后，下次启动核对进程身份和数据锁，保留原有数据。目录被另一个进程占用时不强制删除锁、不终止未知进程。

## 安装状态与错误恢复

区分包安装结果、用户保存的启用选择和实际运行状态。保存了 `enabled` 不表示服务已启动；pnpm 成功只说明包安装完成。

| 状态 | 用户看到的内容 | 可用操作 |
|---|---|---|
| downloading | 正在安装插件和本地分析组件 | 取消 |
| verifying | 正在检查运行环境 | 按当前阶段决定是否可取消 |
| starting | 正在启动本地分析服务 | 查看状态 |
| ready | 已就绪，可以查询文件改动来源 | 开始使用、停用 |
| disabled | 已停用，运行组件已保留 | 启用 |
| needs-repair | 本地分析组件不完整 | 修复并重试、查看详情 |
| failed | 具体失败原因与下一步 | 重试或适用的恢复操作 |
| unsupported | 当前主机暂不支持 | 查看支持平台 |

失败默认展示一条中文原因和对应操作，技术详情折叠显示。示例：

```text
本地分析组件下载未完成
重新下载后会自动启动，已有分析记录会保留。

[修复并重试]  [查看详情]
```

「修复并重试」通过 DSH 包管理服务重装当前精确版本的包，复用 Profile 写锁、注册表/代理配置、取消和诊断机制。不得绕过包管理器临时下载可执行文件。若当前 DSH 接口尚不支持原地修复，首版使用已支持的包重装流程，保留数据目录；通用修复接口单独提交到 DSH。

错误分类必须来自可验证的失败阶段和退出信息：

| 内部错误码 | 用户文案与恢复操作 |
|---|---|
| runtime-download-failed | 本地分析组件下载失败，请检查网络后重试 |
| runtime-missing | 本地分析组件不完整，点击修复并重试 |
| runtime-integrity-failed | 本地分析组件校验失败，重新安装此版本 |
| unsupported-platform | 当前主机暂不支持，列出已验证的平台 |
| insufficient-space | 安装空间不足，释放空间后重试 |
| runtime-launch-blocked | 系统阻止了分析组件启动，查看详细原因；不引导关闭安全防护 |
| data-dir-in-use | 此分析目录正在使用中，关闭占用它的实例后重试 |
| incompatible-core | 分析组件版本不匹配，修复为插件配套版本 |
| startup-timeout | 本地分析服务启动超时，可重试并查看启动日志 |
| unexpected-exit | 本地分析服务意外退出，可重试并查看退出原因 |

未能确定的错误保留为启动失败，不把所有退出都解释为缺少 Core。日志保留阶段、包版本、平台、退出码和经过处理的 stderr；复制诊断时移除凭据及会话内容。

## 网页接入边界

AgentLineage 自己提供运行状态服务和设置入口，使初始化失败后仍能显示恢复操作。控制入口的插件加载成功与 Core 就绪分别记录。

若要让 DSH 通用安装弹窗完整显示「下载、校验、启动、已就绪」，需要 DSH 插件管理器和 UI 增加可选的 readiness 协议。沿用安装 `requestId` 关联状态，但将包操作阶段与插件就绪阶段区分开；包安装成功后订阅插件的状态，超过等待上限则显示「包已安装，启动失败」，保留恢复入口。没有声明 readiness 的其他插件继续使用现有行为。

DSH 当前已有安装日志、`installing` / `applying` 阶段、取消和激活诊断，可以复用这些机制；完整就绪协议及运行包修复按钮属于新增能力，不能只在市场仓库修改文案便声称完成。现有 DSH 版本下先保证依赖随包安装、自动启动和插件设置入口可用；通用弹窗体验随 DSH 接入一起交付。

## 升级与数据

运行包随插件精确版本一起升级。仅有运行包更新、旧包仍在运行时，界面说明需要重新启用或重启；实际生效后再更新运行版本。

先完成新包校验与运行条件检查，再停止旧实例并启动新实例，检查通过才切换到新版本。保持同一个 Profile 只有一个进程拥有数据目录。当前 DSH 更新流程可能先卸载再安装，需在其包管理层实现版本暂存和恢复，不能假定已有原子升级能力。

遇到数据格式迁移，先生成可恢复备份；失败后只有在数据仍与旧版兼容或备份已成功恢复时才能回退旧运行包。首版优先维持当前 Core 数据格式，避免把分发改造与数据库迁移混在一起。

卸载默认保留分析记录和凭据，界面说明保留位置；清除分析数据单独操作。安装或修复失败不会删除用户记录。运行包是只读安装资产，数据继续保存在 Profile 对应的独立目录。

## 后续采用 Node SDK 的条件

已有 `@fuxi-ailabs/agentlineage-core@0.1.0-alpha.1` Node SDK，可在 Node worker 中处理数据，无需 Python。它当前定位为 `harnesscore/v1`，支持 Claude、Codex 和 DevEco，公开 API 不包含 DSH 原生适配、Python 报告检查及 Viewer。因此本次不把替换依赖名当成功能等价迁移。

后续补齐 DSH v4 导入、现有查询、报告检查和 Viewer，并完成证据引用、会话绑定与数据迁移验证后，可以把默认后端换成 Node SDK，减少平台运行包的维护成本。用户界面和「安装后就绪」承诺保持一致。

## 实施顺序与验收

| 改动位置 | 交付内容 |
|---|---|
| AgentLineage 发布流水线 | 构建并发布 Windows x64 完整运行包，清单与精确版本依赖 |
| AgentLineage DSH 集成 | 定位随包运行环境、就绪状态、错误分类、设置与恢复入口、进程生命周期 |
| DSH 插件管理器及 UI | 安装阶段衔接 readiness、重连读取状态、修复和升级恢复能力 |
| 本市场仓库 | 指向已验收的新版本；介绍页改为一键安装流程与支持平台 |

发布前须在无 Python、无 Core、无 Git、无开发环境变量的干净 Windows x64 主机上，从真实 DSH 网页安装最终发布包。验收至少覆盖：

1. 不批准依赖构建脚本，也能自动安装运行包并启动；默认配置无需修改，最终显示「已就绪」。
2. 完成 `lineage_status`、创建文件、两次修改、导入、查询、检查报告和打开 Viewer；核对三次写入及六条原文引用。
3. 安装中断、运行包缺失、文件校验失败、版本不匹配、目录占用和服务启动超时均给出对应提示；恢复后无需卸载 DSH。
4. 关闭网页再打开能继续查看同一任务；取消与安装完成竞争时呈现真实结果。
5. 断网重启 DSH，已安装插件仍可启动和查询本地材料；模型联网要求按 DSH 自身配置处理。
6. 停用后所属进程和端口释放；重启后原快照与绑定可用；多个 Profile 互不占用数据目录。
7. 升级或修复失败保留数据，可按实际支持的恢复路径回到可用版本。
8. 远程浏览器访问时组件安装到 DSH 主机；Viewer 访问必须复用 DSH 已认证的同源入口，或提供受支持的服务端转发，不能把服务端 loopback 地址当成浏览器本机地址。凭据保留在主机，前端不接收 Core token。完整远程体验在该接入验证通过后再列为支持。

Windows x64 的实施与验证结论见安装验收记录。本文其余平台分发、通用安装状态协议和原子升级部分继续作为后续设计，不计为 alpha.4 已交付能力。
